# АМА РС

Техническая основа бота на Python 3.12, MySQL 8.4 и Docker Compose.

## Локальный запуск

1. Скопируйте `.env.example` в `.env` и задайте отдельные пароли для приложения и root.
2. Выполните `docker compose up --build -d --wait`. MySQL поднимется первым, затем Alembic применит миграции и запустится приложение.
3. Выполните `docker compose ps` для проверки состояния. Внутренний endpoint `/healthz` проверяет соединение приложения с MySQL.

Новые миграции можно создавать локально командой `alembic revision -m "описание"` в окружении с зависимостями из `requirements.txt`. Начальная ревизия фиксирует версию схемы. Бизнес-таблицы добавляются миграциями соответствующих модулей.

`docker compose down` останавливает сервисы. Данные MySQL хранятся в именованном томе.

## Сборка за HTTPS-прокси

Если прокси использует собственный CA, передайте доверенный PEM-бандл как секрет сборки `pip_ca`. Например, создайте локальный файл Compose вне репозитория:

```yaml
services:
  app:
    build:
      secrets: [pip_ca]
  migrate:
    build:
      secrets: [pip_ca]
secrets:
  pip_ca:
    file: /etc/ssl/certs/ca-certificates.crt
```

Укажите путь к бандлу своей среды и запустите `docker compose -f compose.yaml -f /путь/к/файлу.yaml up --build -d --wait`.

## Подключение предприятия

Первичное подключение выполняет оператор с доступом к Docker. Подготовьте локальный
JSON и передайте его через stdin:

```sh
docker compose exec -T app python -m ama_rs.setup_enterprise save /dev/stdin --revision 0 --operator admin < enterprise.json
docker compose exec -T app python -m ama_rs.setup_enterprise show branch-1
```

Минимальный пример файла:

```json
{
  "id": "branch-1",
  "iiko_id": "iiko-100",
  "name": "Предприятие 1",
  "format": "delivery",
  "timezone": "Europe/Moscow",
  "server_address": "server.example.invalid",
  "lm_address": "lm.example.invalid",
  "contact_mode": "independent",
  "final_route": "headquarters",
  "brands": ["Бренд 1"],
  "chats": {
    "enterprise": {
      "platform": "telegram",
      "id": "-100111",
      "kind": "enterprise",
      "calendar": [{"weekday": 0, "start": "09:00", "end": "21:00"}]
    }
  },
  "grants": [{"chat": "enterprise", "role": "service_account", "user": "123456"}]
}
```

Целевые чаты задаются отдельными ключами даже при общем чате для нескольких
предприятий. Все идентификаторы пользователей, чатов и тем передаются строками.
В календарях недели понедельник имеет номер 0. Время окончания раньше начала
означает переход через полночь. Для круглосуточного чата укажите `"always"`.
Пустой или отсутствующий календарь закрыт для автоматической доставки.
Для замещений можно задать границы назначения `starts_at` и `ends_at`
в ISO 8601 с часовым поясом. Для обновления укажите текущий номер ревизии.

## Ядро процессов

Функции `ama_rs.processes` выполняются внутри общей транзакции MySQL.
Карточка создаётся по устойчивому ключу источника. Действие проверяет роль,
контекст, назначение и ревизию карточки, а повтор команды возвращает прежний
результат. Фотографии и другие вложения сохраняются как ссылки на файлы
мессенджера с метаданными. Бизнес-модули определяют допустимые переходы.

Очередь хранит один сигнал на карточку и чат. В закрытое окно запись остаётся
в очереди. Отправитель фиксирует попытку до сетевого вызова и подтверждает её
после ответа. Неопределённую попытку требуется сверить перед повторной
отправкой. Таймер, зависящий от доставки, запускается после её подтверждения.

## Сменные чек-листы и касса

Модуль `ama_rs.shifts` содержит сценарии утренней и вечерней смены,
расчёт локального расписания и работу с кассовым комплектом. Передавайте один
устойчивый идентификатор смены в оба сценария. Утренний чек пересчёта и вечерние
документы сохраняются в общей кассовой карточке с отдельным маршрутом.
Окончательная приёмка открывается после подтверждённого события закрытия iiko.

Зоны гостевого зала и санузлов задаются в `facilities`, курьерские терминалы
задаются списком идентификаторов `courier_terminals`. В `shift_schedule`
укажите `service_starts_at`, `service_ends_at` в формате HH:MM,
`preparation_minutes` и `closing_minutes`. До подключения обработчиков
мессенджера и iiko сценарии доступны на уровне сервисных функций.

## Вебхуки и доставка

Профиль `integrations` включает обработчик очереди:
`docker compose --profile integrations up --build -d --wait`.
Для сборки через прокси добавьте `worker` с тем же секретом `pip_ca` в локальный
Compose-файл. Разрешите исходящий HTTPS к `api.telegram.org` и
`platform-api.max.ru` для выбранных платформ.

Перед использованием разместите приложение за HTTPS-прокси с ограничением
размера и времени обработки запросов. Привяжите `/webhooks/telegram` и
`/webhooks/max` к своим ботам. Укажите токены и секреты вебхуков в локальном
`.env`. Команда `/menu` показывает доступные команды. `/tasks` показывает
текущий пункт и слоты фото для назначенного чек-листа.

`POST /webhooks/iiko` обслуживает адаптер нормализованных событий. Адаптер
подписывает точные байты JSON в `X-AMA-Signature` как hex HMAC-SHA256 с
`IIKO_WEBHOOK_SECRET`. Оболочка события содержит `id`, `enterprise_id`
(внешний iiko ID), `type` и объект `data`. Поддерживаются:

| Тип | Поля data |
| --- | --- |
| staff.updated | employee_id, name, profile |
| staff.schedule / staff.attendance | employee_id, source_key, starts_at, ends_at, observed_at |
| shift.checklist_due | phase (morning или evening), shift_id |
| cash_shift.closed | shift_id |
| sales.writeoff / sales.return | document_id и доступные данные операции |

Дата и время событий указываются в ISO 8601 со смещением. Если событие пришло
до обязательного сопоставления или закрываемый кассовый комплект ещё не
передан, HTTP 409 разрешает адаптеру повторить то же событие после устранения
причины. Сопоставление реальных контрактов iiko и регистрация вебхуков требуют
настроек конкретного предприятия и тестовых событий поставщиков.

## Сводки и показатели заказов

Команда `/report YYYY-MM-DD YYYY-MM-DD` показывает управленческую сводку за
локальные даты предприятия. Правая граница исключается. Доступ имеют
управляющий и руководитель филиала в своих рабочих чатах.

Укажите `"scheduled_reports": true` в конфигурации предприятия и запустите
`worker` для ежедневных сводок в управление и недельных/месячных сводок в
руководство филиала. Расчёт начинается с 10:00 по местному времени. Очередь
сохраняет границы периода, пока чат закрыт.

Адаптер iiko может присылать `orders.updated` с полями `order_id`,
`number`, `fulfillment` (`delivery`, `pickup`, `takeaway`, `dine_in`),
`accepted_at`, `updated_at` и доступными `handed_at`, `ready_at` и
`issued_at`. Событие `source.coverage` передаёт `day`, `source`,
`state` (`complete`, `partial`, `unavailable`) и `updated_at`. Данные
об оплате не используются вместо недостающих отметок готовности или выдачи.

## Сквозные проверки

Запустите стек с отдельным именем проекта Compose и отдельным тестовым MySQL.
Задайте тестовый `IIKO_WEBHOOK_SECRET` в используемом env-файле. Затем выполните
`./scripts/smoke.sh --env-file /путь/к/test.env -p ama-rs-test`. Скрипт запускает
двадцать шесть проверок внутри контейнера приложения на реальной тестовой базе.
Для приёмки пилота дополнительно нужны тестовые чаты Telegram/MAX, назначения
ролей и образцы событий из iiko для выбранных предприятий.

`/workflow` перечисляет формы процессов. Команда
`/workflow <операция>` показывает названия полей. Для отправки формы добавьте
JSON, например `/workflow refund.result {"card_id":"…","revision":3,"outcome":"executed","reference":"…"}`.
Права и назначение проверяются по аккаунту, текущему чату и состоянию
карточки. Для передачи кассового фото отправьте команду `cash.document`
в подписи к снимку Telegram.

### Меню и настройки в General

`/menu` открывает кнопки навигации Telegram или MAX. Кнопки личного меню
привязаны к пользователю, чату и теме, действуют 30 минут. Приёмка и взятие
карточки проверяют её версию и назначение.

Для первого системного администратора добавьте роль `system_admin` и
`general_topic_id` в привязку технического Telegram-форума через локальную
команду настройки. Укажите строковый идентификатор темы или явный `null`,
если события General приходят без идентификатора темы. `/settings` и
`/timers` открывают один экран. Например, команда
`/configure branch-1 timing_overrides {"technical.high":[8,16,28]}`
показывает предпросмотр. Кнопка «Сохранить» применяет настройку к новым
этапам. Текущие дедлайны сохраняются.

Проверка результата поручения или техзаявки отсчитывает рабочие минуты от
подтверждённой доставки в чат проверяющего. Финансовый дедлайн и напоминания
сохраняются при принятии заявки и уточнении. По истечении дедлайна без ранее
доставленного напоминания очередь сначала уведомляет финансовый чат. После
подтверждённой доставки отсчитываются десять рабочих минут до филиала.

### Автоматический запуск чек-листов

Установите `scheduled_checklists: true` и запустите `worker`, чтобы запускать
чек-листы по локальному расписанию предприятия. Для ночной смены утро и вечер
имеют один ключ `local:YYYY-MM-DD` по дате открытия. В событии
`cash_shift.closed` можно передать эту дату в `business_day`, чтобы привязать
закрытие iiko к локально запланированной смене. Для предприятий, где запуск
остаётся по событиям адаптера, используется прежний внешний `shift_id`.

Календарь существующего чата можно обновить через предпросмотр, например
`/configure branch-1 chat_calendar {"chat":"enterprise","calendar":"always"}`.

Полный администратор может назначить делегата через
`/configure branch-1 admin_access {"chat":"technical","user":"12345","access":["chat_calendar"]}`.
Значение `"full"` назначает полного администратора, `null` снимает
административные права. Последнего действующего постоянного администратора
снять нельзя. Делегат видит и редактирует только назначенные поля своего
предприятия. Каждое изменение подтверждается кнопкой и сохраняется в истории.

Финансовая эскалация создаёт одну карточку контроля филиала. Если после её
подтверждённой доставки карточку не взяли на контроль, та же карточка
переходит по заранее сохранённому конечному маршруту. Команда
`/workflow refund.control` показывает поля для принятия контроля. Финансовый
запрос закрывает только уполномоченный исполнитель.

Просрочка поручения или технической заявки создаёт связанную карточку
контроля. Реакция отсчитывается в рабочие минуты после доставки каждому
руководителю. Техническая цепочка проходит через технического директора,
операционного директора и генерального директора. Исполнитель продолжает
работу по исходной карточке. Принятый результат закрывает связанный контроль.
Команда `/workflow request.control` принимает контроль с действием и сроком.

Для кассового чата задайте `cash_accept_by` в формате `HH:MM` внутри
его рабочего дня. После доставки закрытой смены бот ставит срок приёмки
на следующий рабочий день и через два рабочих часа эскалирует в филиал.
`/workflow cash.discrepancy` передаёт расхождение в связанную карточку
управляющему, `/workflow cash.explain` возвращает объяснение в кассовую смену.

Для стоп-листов, гоу-листов, изменений доставки и приостановок действует
контроль взятия и выполнения. Центральный режим эскалирует в «Управление
КЦ», самостоятельный — в филиал. Контроль остаётся связанным с исходной
задачей и закрывается вместе с ней.

При массовой задержке бот отсчитывает рабочие минуты до первого обзвона
от принятия задачи или подтверждения готовности конкретного заказа.
Поле `waiting_for_details` перечисляет заказы, для которых ещё не хватает
сведений. Команда `/workflow operation.order_ready` запускает срок для
такого заказа. Напоминания объединяются, а после первой попытки связи
заказ выходит из списка первого обзвона.

В центральном режиме оператор передаёт активную задачу через
`/workflow operation.handoff`. Укажите получателя и заметку. Новый оператор
принимает её из «Мои задачи» или отвечает через `operation.handoff_response`.
Отказ требует причины. До принятия действует прежнее назначение, а после
принятия сроки остаются на исходной карточке. Если по доставленной передаче
нет ответа десять рабочих минут, бот уведомляет «Управление КЦ».

### Смена оператора КЦ

Руководитель назначает смену через `/workflow operator_shift.plan` с
идентификатором предприятия и временем начала и окончания в ISO 8601.
У оператора карточка появляется в «Мои задачи». Первый этап фиксирует
фактическое начало после обязательных проверок, второй — административные
проверки. Скриншоты поступают в «Управление КЦ». Для закрытия нужны итоговые
проверки и завершение или принятая передача активных задач. Сводки до
планового конца смены используют действующие рабочие календари.

[Сверка реализации с ТЗ](docs/spec-coverage.md).

### Отклонения рабочего времени

Для предприятия включите `attendance_monitoring`. Контроль использует
подтверждённые карточки сотрудников, интервалы план/факт и актуальные события
`source.coverage` для `schedule` и `attendance`. Без подтверждения полноты
отсутствие отметки не считается отсутствием сотрудника. При пересечении
нескольких плановых смен неопределённый факт не распределяется автоматически.
Управляющий запрашивает пояснение через `/workflow attendance.question`.
Ответ доступен из подтверждённого личного чата сотрудника.

Исправление документа iiko ведётся в исходном списании, возврате, кассовой
смене или инвентаризации. Управляющий использует `/workflow accounting.request`
и назначает пользователя с ролью `accounting_executor` в существующем чате.
Подробности доступны назначенным пользователям по `/accounting <ID>` в личном
диалоге. Исполнитель фиксирует ручное исправление или отказ, управляющий
проверяет результат. Статус исходного процесса и данные iiko сохраняются.

В General откройте «Настройки предприятия → Готовность к запуску».
Экран показывает отсутствующие маршруты, календари и роли, фактическую
подтверждённую доставку по действующим привязкам и актуальность потоков iiko.
Изменение идентификатора чата или темы требует новой проверки доставки.

Экран «Готовность к запуску → Проверить маршруты» ставит тестовое сообщение
в очередь с учётом календаря. Назначенный участник подтверждает его в той же
теме командой из сообщения. В Telegram для проверки входящего фото команда используется
в подписи к тестовому снимку. Повторный запуск незавершённой проверки использует
ту же запись. Новая привязка чата или темы требует отдельного подтверждения.

В General откройте «Настройки предприятия → Мастер чек-листов». Для нового
маршрута мастер показывает команду добавления чата и ответственной роли.
После настройки расписания и календарей подтвердите тестовую отправку
в чатах предприятия, управления и приёмки кассы. Кнопка подготовки включения
появится после прохождения проверок. Если подтверждённая привязка или роль
изменятся, новые автоматические чек-листы ждут повторной проверки. Уже
созданные чек-листы продолжают работать. Прежние установки, включённые через
локальную настройку, сохраняют действующий режим.

### Создание предприятия из General

Для первого развёртывания используется локальная настройка. Чтобы разрешить
дальнейшее создание предприятий из General, в локальной конфигурации задайте
`"create_enterprises": true` в назначении конкретного `system_admin`.
Администратор получит кнопку «Новое предприятие» и форму с обязательными
полями. После подтверждения создаётся отдельная карточка и открывается
мастер маршрутов. Новая карточка получает привязку текущего General и роль
своего администратора. Полномочие создавать другие предприятия отдельно
задаётся в исходной конфигурации.

В разделе «Включение сценариев» для плановых сводок проверяются чаты
управления и филиала и успешная выгрузка заказов iiko. Для контроля рабочего
времени проверяются чат управления и выгрузки графика и явок. При сохранении
проверки повторяются. Если проверенный маршрут изменится, новые плановые
действия по этому сценарию ждут повторного подтверждения. Прежние установки
через локальную настройку сохраняют действующий режим.

Для исправления можно указать `reserve_chat` и `reserve_user` в
`accounting.request`. Бот использует резерв при снятии текущей роли или
подтверждённом отказе доставки исполнителю. При неопределённой отправке
сохраняется текущий статус доставки. Исполнитель запрашивает пояснение
через `accounting.submit` с исходом `clarification`, управляющий отвечает
через `accounting.answer`. Срок сохраняется.
